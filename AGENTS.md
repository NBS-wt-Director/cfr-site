## 🚫 КРИТИЧЕСКИЕ ПРАВИЛА БЕЗОПАСНОСТИ

### Работа с файлами вне проекта — КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО

При работе над **любым** проектом без **тройного указания** и **особого разрешения** пользователя критической и недопустимой ошибкой является:

1. **Изменение файлов/структуры файлового дерева вне проекта**, в котором запущена модель.
   — Все изменения (создание, редактирование, удаление) разрешены **ТОЛЬКО** в файлах внутри рабочей директории текущего проекта.

2. **Удаление файлов за пределами проекта напрямую**, без подтверждения.
   — Удаление происходит **только** если пользователь ознакомился со списком файлов на удаление в панели плагина.
   — Даже после ознакомления — **только перемещение в корзину**, никогда прямое удаление.

3. **Самовольное изменение падежей и прочих языковых аспектов в абсолютных путях файлов.**
   — Пути к файлам должны сохраняться в точности как есть. Никогда не изменяйте регистр, падежи, транслитерацию или любые другие языковые аспекты в путях.

**Нарушение этих правил = критическая ошибка.** Всегда уточняйте у пользователя перед любыми действиями с файлами вне текущего проекта.

## ⚠️ КРИТИЧЕСКИЕ ПРАВИЛА

### 1. Turbopack ЗАПРЕЩЁН навсегда

Next.js 16 по умолчанию использует Turbopack, который **ломает сборку** (Tailwind CSS генерирует стили, которые Turbopack не может распарсить).

**Всегда используйте Webpack:**
```json
"build": "next build --webpack",
"start": "next start -p 3000"
```

> ⚠️ **Важно:** `next start` в Next.js 16 **не поддерживает** флаг `--no-turbopack` — вызывает ошибку `unknown option`. Используйте только `next start -p 3000`.

Это зафиксировано в:
- `package.json` (scripts dev/build/start)
- `deploy/ecosystem.config.js` (args: 'start -p 3000')

**Никогда не меняйте эти скрипты.** Если `next build` падает с ошибкой `Parsing CSS source code failed` — это Turbopack.

### 2. Секреты — ТОЛЬКО через переменные окружения

**НИКОГДА не хардкодите пароли, токены, ключи в коде.**

Правильно:
```ts
const JWT_SECRET = process.env.JWT_SECRET;
if (!JWT_SECRET) {
  throw new Error('JWT_SECRET не установлен');
}
```

Неправильно:
```ts
const JWT_SECRET = process.env.JWT_SECRET || 'cfr-lk-secret-2026';
```

Обязательные переменные:
- `JWT_SECRET` — для JWT-токенов ЛК (минимум 32 символа, `openssl rand -base64 32`)
- `ADMIN_API_KEY` — для защиты админ-маршрутов (`openssl rand -base64 32`)
- `PG_PASSWORD` — пароль PostgreSQL (`openssl rand -base64 16`)
- `SMTP_PASSWORD` — пароль SMTP (если используется)

Файл `.env.production` должен быть на сервере, но НЕ в репозитории.
Шаблон: `.env.example` — в репозитории, без секретов.

### 3. API маршруты — новый синтаксис
Все файлы в `src/app/api/**/route.ts`:
- `params: { id: string }` → `params: Promise<{ id: string }>`
- `params.id` → `await params`
- `import { db }` → `import { getDb, saveDb }`
- `await db.getData()` → `getDb()`
- `await db.updateXxx()` → `saveDb(data)`

**Не используй:**
- `db.getData()`
- `db.updateNews()`, `db.updateTrainers()` и т.д.
- `import { loadDb }` → используй `getDb()`
- `loadDb()` → используй `getDb()`

### 4. Типизация
- Next.js 16 строго типизирует. Если ошибка типа — используй `as any` для быстродействия.
- `href` может быть `undefined` → добавляй `|| '#'`
- `photoAlbum` может быть `undefined` → используй `as any[]`
- Функции-обработчики должны принимать `File | null`, не просто `File`

## 📋 МУЛЬТИТИКЕТЫ — ФОРМАТ КОМАНД

### Формат

**Три строки. Больше ничего:**

```
Прочитай документ <путь к MULTITICKET.md>
и выполни тикет <N>
```

**Пример:**

```
Прочитай документ cfr-site/MULTITICKET-DANCESTUDIO.md
и выполни тикет D1
```

### Что делает AI

1. Читает указанный файл мультитикета
2. Находит указанный тикет по номеру
3. Читает тикет полностью
4. Выполняет код задания

### Почему минимум слов

- Лишние слова путают — AI может проигнорировать контекст
- Чёткая структура "прочитай документ + выполни тикет" — надёжнее длинных инструкций
- Номер тикета = точка входа. AI сам найдёт и прочитает весь контекст

### Исключения

Это правило касается только команд на выполнение тикетов мультитикетов.
Обычные вопросы и задачи выполняются без этого формата.

## 🎫 СИСТЕМА ТИКЕТОВ — КОРНЕВЫЕ ПРАВИЛА

**Записано 2026-11-07 по указанию пользователя. Действует во всех проектах монорепо.**

### Структура каталога `tickets/`

```
tickets/
├── README.md          ← корневой документ: правила + индекс-указатель (точка входа в новой сессии)
├── activ/             ← активные и спорные тикеты (каждый — отдельный .md с ПОЛНОЙ информацией)
│   ├── withLord/      ← тикеты, где обязательно участие пользователя (SSH, решения, git-мутации)
│   └── periodic/      ← периодические задачи (деплой, проверка, тесты, синк данных, уборка)
├── definded/          ← отложенные тикеты (готовы к выполнению, ждут решения/разблокировки)
└── done/              ← выполненные тикеты (переносятся по завершении)
```

### Правила

1. **Каждый тикет — отдельный файл** с полной информацией: цель/постановка, факты, шаги, критерий готовности.
2. **Источник тикетов** — мультитикет-документ проекта (для статики — `tickets/activ/` и `tickets/definded/`);
   `tickets/README.md` — **индексный/адресный указатель**: по нему в новой сессии видно,
   что активно, что отложено, где нужно участие пользователя, и где лежит полный текст тикета.
3. **Выполненные тикеты переносятся в `tickets/done/*.md`**: текст не меняется,
   в шапку добавляется строка `> Закрыт: <дата>, <итог>`. Строка тикета в индексе
   перемещается в таблицу «Выполненные».
4. **Спорные тикеты** (закрытие не подтверждено журналом) остаются в `activ/` с пометкой ⚠️,
   пока закрытие не будет подтверждено проверкой кода/тестов.
5. **Периодические тикеты** (`periodic/`) не переносятся в `done/` — они живые регламенты
   с чек-листом и журналом выполнений внизу файла.
6. **Порядок работы в новой сессии:** прочитать `tickets/README.md` → найти тикет в индексе →
   прочитать файл тикета → выполнить → обновить ЖУРНАЛ исходного документа.

### Стандартные команды тикет-системы

**«продолжай»** — продолжить выполнение: взять следующий тикет из активной очереди
(по индексу `tickets/README.md`, в порядке очереди волны), дочитать незавершённый
или разблокировать следующий шаг. Начинать без дополнительных вопросов.

**«добавь задачу»** — добавить тикет(ы) в систему по схеме:

```
добавь задачу:
- *{ пункт задачи 1 }
- { пункт задачи 2 }
- ...
- *{ пункт задачи N }
```

где `*` — обязательный/приоритетный пункт, без `*` — обычный. AI создаёт файл
`tickets/activ/<идентификатор>-<короткое-имя>.md` с полной структурой тикета,
добавляет строку в индекс `tickets/README.md`.

**«приберись в задачах»** — уборка каталога `tickets/`:
1. перенести выполненные тикеты в `tickets/done/` (с датой закрытия);
2. размороженные — из `definded/` в `activ/` (и наоборот — приостановленные в `definded/`);
3. обновить индекс-указатель `tickets/README.md` (актуальные статусы и пути);
4. удалить дубли и устаревшие записи; неактуальное — только в `trash/`, не удалять напрямую.

## 🎨 CSS: ЗАПРЕЩЁНЫ вложенные комментарии

**Записано 2026-11-09 по факту бага S143.**

- **CSS-комментарии `/* ... */` НЕ ВЛОЖЕННЫЕ.** Внутренний `/*` не создаёт вложенность —
  первый `*/` закрывает комментарий ДОСРОЧНО.
- Всё, что между `*/` и следующим `{...}`, парсер считает мусором (bad rule recovery)
  и **ДРОПАЕТ** это правило — оно физически не применяется в браузере.
- **Корневой баг S40/S99/S109/S139/S141/S143:** вложенный `/* S79... */` на строке 88
  style.css закрывал комментарий досрочно → мусор на строке 89 → правило
  `[hidden] { display: none !important; }` ДРОПАЛОСЬ → картинки расписания
  показывались в режиме «Таблица» (S40/S99/S109/S139). **9 лет!**
- **Правило:** никогда не писать `/* ... /* ... */` в CSS. Если нужен вложенный текст —
  используйте `--` (deux-tirs) или другой разделитель, а не `/* */`.
- **Регресс-тест:** `scripts/test-static.mjs` проверяет парсер CSS на вложенные комментарии.
