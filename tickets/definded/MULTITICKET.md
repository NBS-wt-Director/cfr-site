# МУЛЬТИТИКЕТ: Перевод сайта на PostgreSQL + ЛК

> ⚠️ **ВНИМАНИЕ:** Эта задача разбита на 5 тикетов (сессий).
> Тикеты связаны жёсткими зависимостями — **разрывать порядок нельзя**, иначе сломаются данные.
> Каждый следующий тикет опирается на результат предыдущего.

## Контекст

Сайт `cfr-site` (Next.js 16, lowdb/JSON) нужно перевести на PostgreSQL с табличной структурой.
Режим работы — двухрежимный: JSON (по умолчанию) ↔ PostgreSQL (переключается из админки).
Данные в PG хранятся **по таблицам** (trainers, programs, news, ...), а не в куче.
Чтение в PG-режиме — **реальное** (из БД, не из кэша).
Дополнительно: создан Личный Кабинет (ЛК) клиента.

  - 💰 Мои оплаты — таблица с итоговой суммой
  - 📅 Мои посещения — таблица с итоговым количеством
  - 📝 Запись на тренировку — заглушка "Скоро"
  - 💻 Онлайн тренировки — заглушка "Скоро"
- ✅ `lk/page.module.css` — стили
- ✅ Установлены `bcryptjs`, `jsonwebtoken`, `xlsx`

### Логика работы ЛК:
1. Клиент просит у администратора дать ключи доступа
2. Администратор в админке (вкладка 🔑 ЛК → 👥 Пользователи) создаёт ключ:
   - логин = номер телефона клиента
   - пароль = 6-значный код (генерируется автоматически)
3. Администратор передаёт клиенту логин и пароль
4. Клиент входит в ЛК (/lk) используя эту пару
5. Администратор регулярно загружает данные из Excel (CRM) через вкладку 📥 Импорт Excel
6. В ЛК клиент видит только свои оплаты и посещения (только просмотр, без оплаты онлайн)

## Тикет 6: Миграция из админки (безопасный перевод JSON → PostgreSQL)

**Статус:** 🔴 **НЕ ВЫПОЛНЕНО** — процесс миграции запускается через админку

### Контекст и критические правила (ОБНОВЛЕНО)

1. **Никогда не запускать проект с Turbopack.** Всегда использовать Webpack:
   - `dev`: `"next dev --webpack -p 3011"` (в package.json уже исправлено)
   - `build`: `"next build --webpack"`
   - `start`: `"next start --no-turbopack -p 3000"`

2. **db.json — ИСТОЧНИК ИСТИНЫ.** Никогда не удалять, не очищать, не перезаписывать.
   - db.json остаётся на сервере как fallback
   - db.json НЕ попадает в git (уже в .gitignore)
   - data/*.json НЕ попадает в git
   - .db-mode.json НЕ попадает в git
   - .env НЕ попадает в git

3. **Двухрежимность:** сайт работает либо по JSON, либо по PostgreSQL.
   - Переключение через админку (вкладка 🗄️ Данные)
   - До переключения — сайт работает по JSON
   - После переключения — сайт работает по PostgreSQL
   - Данные отображаются корректно в обоих режимах

4. **После перехода на PostgreSQL не пополнять db.json новыми данными.**
   - Все изменения вносятся только в PostgreSQL
   - db.json остаётся только как fallback

5. **Если режим снова переключается в JSON, данные должны читаться из db.json, а не из PostgreSQL-кэша.**

6. **Обратное переключение из PostgreSQL в JSON не реализовывать и не проектировать.**
   - Переключение только JSON → PostgreSQL
   - Без отката

### Процедура миграции (запускается из админки, не вручную)

Через AdminDataTab.tsx должна быть кнопка **"🚀 Перенести данные в БД"**, которая выполняет:

**Шаг 1: Создать Docker-контейнер с PostgreSQL**
- Запустить `docker compose up -d`
- Проверить, что контейнер запущен (`docker compose ps`)
- Сигнализация: ✅ "Контейнер запущен" или ❌ с ошибкой

**Шаг 2: Инициализировать таблицы в PostgreSQL**
- Выполнить `npm run init-db` (запускает docker/init.sql)
- Создать 18 таблиц: trainers, programs, news, sliders, schedule_items, prices, sections, staff, workouts, settings, users, user_visits, user_subscriptions, user_payments, db_meta
- Сигнализация: ✅ "Таблицы созданы" или ❌ с ошибкой

**Шаг 3: Перенести данные из JSON в PostgreSQL**
- Выполнить миграцию: прочитать db.json → записать в PG по таблицам
- Использовать `src/app/api/admin/migrate-db/route.ts` (уже существует)
- Сигнализация: ✅ "Данные перенесены. Всего записей: N" или ❌ с ошибкой

**Шаг 4: Переключить режим на PostgreSQL**
- Если шаги 1-3 успешны — вызвать `/api/admin/db-mode` с `mode: "postgres"`
- Обновить .db-mode.json
- Сигнализация: ✅ "Переключено на PostgreSQL"

**Важно:**
- Кнопка "🚀 Перенести данные в БД" запускает весь процесс целиком (шаги 1-4 последовательно)
- **Пошаговая индикация прогресса** — каждый шаг показывает статус (выполняется/успех/ошибка)
- **Сохранение текущего шага** — после перезапуска процесс может продолжиться с места остановки
- Отдельную кнопку "Включить PostgreSQL" **НЕ добавлять**
- Если любой шаг 1-3 провалился — режим НЕ переключается, db.json остаётся как есть
- После успешной миграции db.json **не удалять** — он остаётся как fallback

### Требования к обоим окружениям

Процесс миграции должен работать одинаково:
- **На dev-машине** (текущая): Docker Desktop / Docker
- **На прод-сервере** (Ubuntu Server): Docker

- Автоматический запуск PostgreSQL при старте системы (systemd service для Docker)
- Постоянное хранение данных в Docker-томах (не в контейнере)
- После миграции — данные хранятся в PG, db.json остаётся как backup

- [ ] Пошаговая индикация прогресса (каждый шаг показывает статус)

## Тикет 8: Парсер Excel под структуру CRM ЦФР

**Статус:** 🔴 **ОЖИДАЕТ ФАЙЛЫ** — файлы загружены в `excel/lk/`

### Источники данных

**Файлы находятся в:** `excel/lk/`

1. **clients.xlsx** (152 КБ, ~1900 строк) — основной источник пользователей
   - 1 лист
   - 10 колонок:
     1. `ФИО` — имя клиента (с возрастом в скобках, например "Абакумов Владимир (66 лет)")
     2. `Дата рождения` — дата рождения
     3. `Пол` — м/ж
     4. `Мобильный 1` — основной телефон (формат 8900... или 7900...)
     5. `Мобильный 2` — дополнительный телефон
     6. `Мобильный родителя 1` — телефон родителя (для детей)
     7. `Мобильный родителя 2` — телефон родителя (для детей)
     8. `Узнал от друга` — источник
     9. `Баланс ЛС` — баланс лояльности (число, может быть отрицательным)
     10. `Дата создания` — дата регистрации в CRM

2. **data.xlsx** (2,3 МБ, ~150 000 строк) — история посещений и оплат
   - 1 лист
   - 7 колонок:
     1. `Посещение` — дата посещения (если пусто — не посещение)
     2. `Клиент` — ФИО клиента
     3. `Группа` — название программы/группы (например "Тайцзи Цигун Кузнецов Александр Вячеславович")
     4. `Вид занятия` — тип занятия
     5. `Оплачено` — сумма оплаты (например "50%, пм - 360" или "без %, пм - 720" или пусто)
     6. `Долг` — долг (число, может быть отрицательным)
     7. `Примечание` — примечание

### Логика парсинга

#### 1. Создание пользователей (из clients.xlsx)

- Пользователь создается **один раз** из `clients.xlsx`
- **Приоритет телефона:**
  1. `Мобильный 1`
  2. Если нет — `Мобильный 2`
  3. Если нет — пропустить строку
- **Телефон не приводить к формату +7900...**:
  - Формат 8900... или 7900... оставлять как есть
- **Имя пользователя:**
  - Из поля `ФИО` извлекать только ФИО, убирать возраст в скобках
  - Пример: "Абакумов Владимир (66 лет)" → "Абакумов Владимир"
  - Возраст считать отдельно по `Дата рождения`, если есть
  - ФИО + возраст использовать только как индекс для сопоставления/поиска, а не как значение имени
- **Поля пользователей:**
  - `phone` — телефон (из приоритета выше)
  - `name` — ФИО без возраста
  - `email` — null (нет в CRM)
  - `created_at` — из `Дата создания`
  - `birth_date` — из `Дата рождения` (если есть)
  - `gender` — из `Пол` (если есть)
  - `balance` — из `Баланс ЛС` (если есть)
  - `parent_phone_1` — из `Мобильный родителя 1` (если есть)
  - `parent_phone_2` — из `Мобильный родителя 2` (если есть)
  - `source` — из `Узнал от друга` (если есть)

#### 2. Обработка посещений и оплат (из data.xlsx)

**Определение типа строки:**
- Если колонка `Посещение` заполнена — это **посещение**
- Если колонка `Посещение` пустая — это **не посещение**
- Каждая строка — это новый факт: либо посещение, либо оплата, а не дубликат пользователя

**Посещение:**
- `visit_date` — значение из колонки `Посещение`
- `user_phone` — значение из колонки `Клиент` (нужно сопоставить с пользователем из clients.xlsx)
- `program_name` — значение из колонки `Группа` (сохранять как есть, не разбивать)
- `notes` — значение из колонки `Примечание` (если есть)

**Оплата:**
- Если колонка `Оплачено` есть значение (не пусто) — это **оплата**
- Формат значения: `"50%, пм - 360"` или `"без %, пм - 720"` или `"пм - 360"`
- **Извлечение суммы:**
  - Число после `"пм - "` сохранять как `amount` (сумма оплаты)
  - Если `"пм - "` не найдено — сумму не создавать
- **Извлечение скидки:**
  - Часть до `"пм - "` (например `"50%, "` или `"без %, "`) сохранять в `discount` (если есть)
  - Если скидки нет — поле пустое
- `payment_date` — дата (если есть в `Посещение`, иначе текущая дата)
- `user_phone` — значение из колонки `Клиент` (нужно сопоставить с пользователем из clients.xlsx)
- `program_name` — значение из колонки `Группа`
- `notes` — значение из колонки `Примечание`

**Долг:**
- Сохранять как есть по знаку:
  - Отрицательное значение — сумма долга
  - Положительное значение — остаток / переплата
- Не переинтерпретировать, не менять знак

#### 3. Сопоставление пользователей с данными

- Пользователь создаётся один раз из `clients.xlsx`
- В `data.xlsx` колонка `Клиент` содержит ФИО клиента (с возрастом, например "Цыганова Елена (51 год)")
- **Нужно сопоставлять по ФИО** (без возраста), а не по телефону
- Если пользователь с таким ФИО не найден — пропустить строку с ошибкой
- Дубликаты пользователей не создавать

#### 4. Колонка Группа

- **Пока данные программ/тренировок в PostgreSQL не загружены**, строку из `Группа` нужно:
  - Сохранять как есть (не разбивать на программу и тренера)
  - Не пытаться нормализовать
  - Строка должна оставаться в исходном распарсенном виде
  - Связь с тренировкой можно показывать потом по клику во всплывающем окне
  - Формат: программа + тренер + время (если есть) — всё в одной строке

#### 5. Родители и вкладки

- У родителей есть отдельные вкладки для каждого ребенка и второго родителя
- Учитывать при парсинге: данные могут приходить не только из основной карточки клиента
- Поля `parent_phone_1` и `parent_phone_2` могут использоваться для сопоставления детей с родителями

### Требования к ЛК

**Все значения в ЛК должны быть пояснены:**
- Любое поле, отображаемое в ЛК, должно иметь понятный смысл/подпись/описание
- Если значение может быть неоднозначным, в интерфейсе нужно явно указать его назначение или расшифровку
- Примеры пояснений:
  - `Баланс ЛС` → "Баланс лояльности (начислено/потрачено)"
  - `Долг` → "Текущий долг (отрицательное — должен, положительное — переплата)"
  - `Скидка` → "Скидка на оплату (например 50%)"
  - `Группа` → "Программа/тренер/время (название из CRM)"
