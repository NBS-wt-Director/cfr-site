# ARCH-003 — Fastify-каркас + pg-адаптер readDb/saveDb (переезд админки)

> **Статус:** 📋 Запланирован (2026-11-14). Блокируется ARCH-002.
> Поставлен 2026-11-14.

## Постановка

Серверное приложение (сайт+админка) — одно Node-приложение на **Fastify** в контейнере `app`.
Первым шагом переезжает **админка** (60+ API-ручек `admin-server.mjs`) с минимальным поведенческим
диффом: **1:1 текущему API**. Хранилище — PostgreSQL (ARCH-002).

## ФАКТЫ

- Все ручки читают/пишут через `readDb()/saveDb()` — форма данных: плоский объект
  `{news, programs, trainers, sliders, ... , settings-ключи}` (flattenDb).
- Самописный multipart-парсер загрузок (`parseMultipart`), анти-спам лидов, JWT-аналог сессий,
  `spawn('npm run static:export')` после сохранений — до ARCH-004 остаётся как есть.
- Ожидаемая нагрузка: десятки запросов/сутки — узких мест нет.

### pg-адаптер (главный узел тикета)
`scripts/pg/store.mjs`:
- `readDb()` → один кэш-объект в памяти (flat-форма, байт-в-байт как flattenDb(db.json)).
  Кэш инвалидируется на любой записи. Первый read — загрузка ~22 SELECT (сотни мс, однократно).
- `saveDb(db)` → транзакция `BEGIN`: delete+insert изменённых таблиц/ключей → `COMMIT`.
  Глобальная очередь записей (мьютекс) — параллельных сохранений не бывает, но защита нужна.
- `validateDbData()` — та же защита S140 перед записью.
- Все хендлеры **не трогаются**: меняются только импорты readDb/saveDb.

### Переезд приложения
1. `app/server.mjs` — Fastify: регистрация плагинов, статика `/admin.html`, все маршруты
   `/api/admin/*` переносятся таблицей «route → handler» (механический перенос функций).
2. Загрузки файлов — `@fastify/multipart` (лимит 50 МБ как `client_max_body_size`), запись в
   `static/uploads/` (том) с теми же именами `{ts}-{rand}.{ext}`.
3. `checkEventsTransitions()` (S166), graceful shutdown, журнал `logs/` — переносятся как есть.
4. Контейнер `app` переключается с `admin-server.mjs` на `app/server.mjs` (compose, ARCH-001).
