## КОНТЕКСТ И ПРАВИЛА

### Архитектурные принципы новой БД

1. **Никаких вложенных таблиц** — всё в плоских таблицах
2. **Никаких `jsonb`** — кроме одной таблицы-очереди моста (`bridge_queue`)
3. **Лучше 20 плоских таблиц, чем 4 дерева** — нормализация до 3NF
4. **Enums вместо бинарных/строковых флагов** — везде, где есть конечный набор предопределённых значений
5. **Всё из донора должно быть учтено** — ни одна сущность не теряется
6. **Удалённые данные не берём** — только актуальные XML-файлы (без LastSave/, Options/, Files/)

### Мост данных (Bridge)

- Админский ПК (Win11) → API сайта
- Формат: пакеты JSON, ответ — статус `пакет номер N — получен` / `пакет номер N — успешное добавление`
- После успешного добавления пакет N удаляется из очереди
- Таблица `bridge_queue` — **единственная**, где разрешён `jsonb`
- Как только данные попадают в `bridge_queue` — они **автоматически** переносятся в соответствующие таблицы СУБД (триггеры/DB functions)

### Технологии

- **СУБД:** PostgreSQL
- **Мост:** PowerShell (без установки доп. ПО, не блокируется антивирусом, автозапуск через Task Scheduler)
- **Донор:** XML-файлы DanceStudio (`данные/_DB/`)
- **Сайт:** текущий стек проекта

### ⚠️ КРИТИЧНО: Стратегия работы с XML

**Донор-база: 140 МБ, 64 XML-файла. AI НЕ МОЖЕТ читать XML напрямую — контекст сессии ограничено (~128-200K токенов, 3 файла убивают сессию).**

**Стратегия:**
1. AI **пишет Node.js скрипт**, который читает все XML и сохраняет результаты на диск
2. AI **запускает скрипт** — скрипт сам читает XML, AI только проверяет результат
3. AI **работает только с JSON-результатами** (json_schema.json, json_summary.json — суммарно ~500 КБ, влезает в контекст)
4. XML-файлы больше не читаются

**Почему это работает:** Node.js скрипт работает на диске, не в контексте сессии. JSON-результаты — маленькие (схемы и сводки, без данных).

### ⚠️ Сегментация

Файлы с похожими названиями имеют **одинаковую структуру**, это партиции одной сущности:

| Сущность | Файлы | Описание |
|---|---|---|
| **SingleTraining** | `SingleTraining.xml` + `SingleTraining001–014.xml` (15 файлов) | Визиты клиентов (крупнейший объём данных) |
| **Account** | `Account.xml` + `Account001.xml` (2 файла) | Абонементы |
| **Client** | `Client.xml` + `Client001.xml` (2 файла) | Клиенты |

Скрипт должен объединять партиции в единые сущности.

**Задача:** написать Node.js скрипт, который читает все XML-файлы донора и сохраняет структуру и сводки на диск.

**Что сделать:**

2. Скрипт должен:

   - Для каждого XML-файла извлечь:
     - **Структуру** (root tag, все поля, типы данных, связи)
     - **Сводку** (количество записей, примеры значений)
     - **UUID клиентов** (из Client.xml + Client001.xml)

   - Сохранить результаты:
     - `cfr-site/данные/DB/json_schema.json` — полная схема всех сущностей (структура, без данных)
     - `cfr-site/данные/DB/json_summary.json` — сводка по каждой сущности (record_count, fields, types, sample_values)
     - `cfr-site/данные/DB/client_uuids.json` — список всех UUID клиентов

**Формат json_schema.json (~200 КБ):**
```json
{
  "client": {
    "root_tag": "Client",
    "item_tag": "Item",
    "fields": [
      {"name": "ID", "type": "UUID"},
      {"name": "FirstName", "type": "string"},
      {"name": "LastName", "type": "string"},
      {"name": "Phone", "type": "string"},
      {"name": "BirthDate", "type": "string (DD.MM.YYYY)"},
      ...
    ]
  },
  ...
}
```

**Формат json_summary.json (~300 КБ):**
```json
{
  "client": {
    "record_count": 15234,
    "fields": ["ID", "FirstName", "LastName", "Phone", "BirthDate", ...],
    "field_types": {"ID": "UUID", "FirstName": "string", ...},
    "sample_values": {"Phone": "+7...", "BirthDate": "DD.MM.YYYY"},
    "source_files": ["Client.xml", "Client001.xml"]
  },
  ...
}
```

**Формат client_uuids.json (~50 КБ):**
```json
["uuid1", "uuid2", "uuid3", ...]
```

> **Важно:** AI НЕ читает XML-файлы. AI пишет скрипт, скрипт читает XML, AI проверяет результат.

### Тикет 2.2: Мост данных для админского компьютера + API-эндпоинты

**Задача:** создать PowerShell-скрипт моста и API для его приёма.

**Что сделать — Мост (PowerShell):**

1. Создать `scripts/bridge_agent.ps1`:
   - Автозапуск через Windows Task Scheduler (при входе в систему)
   - Автосканирование папки данных на админском ПК
   - Очередь отправленных пакетов (локальный JSON-файл)
   - Настраиваемые параметры:
     - `queue_folder` — папка очереди
     - `data_folder` — папка данных (путь к XML на Win11)
     - `interval_seconds` — интервал сканирования (по умолчанию 60)
     - `api_endpoint` — URL API-эндпоинта сайта
   - Не требует установки дополнительного ПО (только PowerShell, который есть на Win11)
   - Не блокируется антивирусом (простой скрипт, без динамической генерации кода)
   - Отправка пакетов: `Invoke-RestMethod` → POST на API
   - Обработка ответа: парсинг статуса, удаление обработанных пакетов из очереди
   - Retry-логика при ошибках сети
   - Логирование в файл

2. Создать файл конфигурации `scripts/bridge_config.json`:
   ```json
   {
     "queue_folder": "C:\\dance_studio_sync\\queue",
     "data_folder": "C:\\DanceStudio\\Data",
     "interval_seconds": 60,
     "api_endpoint": "https://your-site.com/api/bridge/receive"
   }
   ```

**Что сделать — API (сайт):**

1. Создать API-эндпоинты:
   - `POST /api/bridge/receive` — приём пакета от моста
     - Принимает JSON-пакет
     - Записывает в `bridge_queue`
     - Возвращает: `{"status": "received", "packet_id": N}`
   - `GET /api/bridge/status` — статус моста (сколько пакетов в очереди)
   - `POST /api/bridge/process` — ручной запуск обработки очереди (опционально)

2. Обработка пакета:
   - Парсинг JSON → вставка в `bridge_queue`
   - Автоматический запуск триггера для переноса в целевые таблицы

**Файлы:**
- `scripts/bridge_agent.ps1`
- `scripts/bridge_config.json`

## ЭТАП 5: ДЕПЛОЙ И МЕДИА-ФАЙЛЫ

### Тикет 4.1: Медиа-файлы — анализ, конвертация, деплой

**Задача:** корректно захватить медиа-файлы из `данные/_DB/Files/`, конвертировать в веб-формат, привязать к клиентам, настроить деплой.

**Контекст:**
- 440 UUID-папок, каждая содержит 1 JPEG-файл
- UUID папки = UUID клиента (связь через Client.xml)
- Форматы: все JPEG, но разные размеры (от 299×222 до 2407×2890)
- EXIF: Yandex.Disk, Adobe Photoshop, Sony ILCE-7S
- Некоторые UUID папок могут не иметь соответствия клиенту (потерянные фото)

**Что сделать:**

#### 4.1.1 Скрипт обработки медиа

Создать `scripts/process-media.mjs`:

1. **Сканирование:**
   - Пройтись по всем 440 UUID-папкам
   - Для каждой: формат, размер, разрешение, вес файла
   - Сопоставить UUID папки с UUID клиентов

2. **Результаты:**
   - Сколько клиентов имеют фото
   - Сколько UUID папок НЕ нашли соответствия (потерянные фото)
   - Средний размер фото, мин/макс разрешение

3. **Конвертация в веб-формат:**
   - Оригиналы сохраняются как есть (JPEG → WebP)
   - Генерация thumbnail (200×200) для списков
   - Генерация medium (640×640 max) для профиля
   - Сохранение:
     ```
     storage/photos/
       {client_uuid}.webp          — основной (до 1920px max dimension)
       {client_uuid}_thumb.webp    — thumbnail
       {client_uuid}_medium.webp   — medium
     ```

4. **Запись в БД:**
   - Для каждого клиента с фото:
     - `INSERT INTO user_photos (user_id, image_url, original_filename, width, height, file_size, format)`
   - Клиенты без фото: поле `photo_url` в users = NULL

5. **Клиенты без фото:**
   - Создать список UUID клиентов без фото
   - Этот список — для администратора: нужно узнать, у кого нет фото

#### 4.1.2 Структура хранения на сервере

```
storage/
  photos/
    {uuid}.webp          — основной
    {uuid}_thumb.webp    — thumbnail
    {uuid}_medium.webp   — medium
```

- Папка `storage/photos/` — не в git (в `.gitignore`)
- На сервере — создаётся при деплое
- URL-доступ: `/photos/{uuid}.webp`

#### 4.1.3 Деплой

1. Обновить `DEPLOY.md`:
   - Инструкция: `node scripts/process-media.mjs` — запуск до деплоя
   - Копирование `storage/photos/` на сервер
   - Настройка веб-сервера для раздачи статики

2. Обновить `.gitignore`:
   - `данные/_DB/Files/`
   - `storage/photos/`
   - `*.webp`

3. **Важно:** медиа-файлы НЕ в git (слишком большие, 440 файлов)
   - Либо: Git LFS
   - Либо: отдельный архив для деплоя
   - Либо: копирование через rsync при деплое

#### 4.1.4 Отображение на сайте

- В ЛК клиента: показывать его фото
