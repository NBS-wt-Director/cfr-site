## П.1. Перевод сайта на Node.js-субфреймворк + PostgreSQL

**Цель:** аккуратно перевести текущую статику (`static/` + `admin-server.mjs` + `db.json`)
на фреймворк Node.js с нормальной маршрутизацией и PostgreSQL как БД.

**Кандидаты (сравнить перед решением):**

| Фреймворк | Плюсы под наши задачи | Минусы |
|-----------|----------------------|--------|
| **Next.js 16** | уже был в проекте (архив `trash/`), SSR/SSG из коробки, API routes | Turbopack ломает Tailwind (правило №1 AGENTS.md, обход `--webpack`); тяжёлый |
| **Nuxt 3** | SSR/SSG, отличная админ-экосистема | смена языка фреймворка (Vue вместо React-стека прошлого опыта) |
| **AdonisJS 6** | монолит «всё включено»: auth, Lucid ORM для psql, IoC; лёгкий | менее популярен, меньше готовых решений |
| **Fastify + Vue/React SPA** | минимальная поверхность, быстрый API, контроль | сборку страниц/SEO/админки пишем сами |
| **Astro** | контентные страницы + islands, статика+гидрация идеально под сайт-визитку с админкой | CRM/ЛК — не его стихия, API тонкий |

**Предварительная рекомендация (к обсуждению):** **AdonisJS 6** — один фреймворк закрывает
и API, и ORM (PostgreSQL), и аутентификацию для CRM/ЛК (п.3); либо **Astro + Fastify**,
если приоритет — витрина с SEO и лёгкость. Решение фиксируется отдельным тикетом-сравнением.

**Связанные тикеты:** `../tickets/definded/NEXT-001-next-return-3-apps.md` (план возврата
Next.js: 3 приложения + PG в Docker + docker-compose — пересмотреть при выборе),
`../tickets/definded/MULTITICKET.md` (миграция PostgreSQL, T1–T4 выполнены).

**Шаги:**
1. Тикет-сравнение:PoC 2–3 кандидатов на малом объёме (одна страница + API + psql).
2. Схема PostgreSQL (перенос структуры `db.json`: data/settings/sections/visits/staff/sliders).
3. Миграция данных `db.json → psql` + сверочный скрипт (count/checksum по каждой таблице).
4. Перенос витрины (страницы/дизайн `static/css/style.css` сохраняем как есть).
5. Перенос админки (`admin-server.mjs` → фреймворковые маршруты; `validateDbData` — в слой репозитория).
6. Двойной прогон: прод-дамп в новую базу, тесты `test-static` переписываются под новый рендер.
7. Деплой параллельно (старый сайт жив, новый на поддомене) → приёмка → переключение NGINX.

**Критерий готовности:** сайт и админка работают на новом стеке + psql, данные 1:1
с прод-дампом, тесты зелёные, откат на текущую статику возможен одной командой.

## П.2. Забор данных из старой CRM DanceStudio

**Цель:** спроектировать, написать и **проверить** скрипт выгрузки данных из старой CRM
DanceStudio (XML/DOCX-доноры, структура известна из сканов).

**Связанные документы/тикеты:**
- `../tickets/definded/MULTITICKET-DANCESTUDIO.md` (1/15 выполнен — D1.4);
- `../info/DANCESTUDIO-SCANS.md` (сканы XML-донора D1.1–D1.7 + маппинг);
- `../info/DANCESTUDIO-SCANS_analis.md` (оценка структуры, DDL-решения, правила импорта);
- `../info/DONOR-FORMAT-ANALYSIS.md` + `../tickets/definded/TICKET-DONOR-FORMAT.md`.

**Шаги:**
1. Инвентаризация источников: где лежит DanceStudio (доступ к БД/экспорт/файлы), формат, объём.
2. Спецификация: таблица маппинга «поле донора → наша сущность» (клиенты, занятия,
   абонементы, платежи, расписание) — на основе существующих сканов.
3. Скрипт `scripts/import-dancestudio.mjs`: dry-run (отчёт) / apply (в staging-таблицы psql),
   идемпотентный (повторный запуск не дублирует).
4. Проверка: сверочный отчёт (количества, выборочные ФИО/даты), тесты на фикстурном дампе.
5. Only после приёмки отчёта пользователем — загрузка в боевую базу.

**Критерий готовности:** скрипт прогнан на реальных данных в dry-run, отчёт сверен
и принят; apply на staging не теряет записи и не дублирует при повторе.

## П.3. Своя CRM (отдельный поддомен) + свой Личный кабинет

**Цель:** спроектировать и реализовать CRM ЦФР на поддомене (например `crm.центр-фр.рф`)
и собственный ЛК клиента (замена текущего `lk.html` + balloo-ЛК).

**Зависит от:** п.1 (фреймворк + psql) и п.2 (данные DanceStudio — исторические клиенты).

**Функциональный контур CRM (черновик, уточнить с пользователем):**
- клиенты и контакты (из п.2 + новые заявки с сайта через `visits`/формы);
- абонементы/посещения/оплаты; расписание и запись;
- коммуникации: шаблоны писем/SMS/соцсетей (перекрёстно с п.4);
- роли: администратор / менеджер / тренер; аудит-лог.

**Функциональный контур ЛК:**
- расписание и записи клиента, история посещений/оплат;
- уведомления (боты, п.5);
- авторизация: JWT (текущий механизм) или сессии фреймворка — решить в п.1.

**Шаги:** 1) ТЗ с пользователем (закрыть контур выше); 2) схема БД; 3) MVP CRM
(клиенты + расписание + оплаты); 4) MVP ЛК (чтение своего расписания/истории);
5) поддомен + NGINX + TLS (команды — через пользователя); 6) перенос существующих
данных заявок/посещений.

**Критерий готовности:** менеджер ведёт клиентов и оплаты в CRM; клиент видит своё в ЛК;
данные с сайта (заявки, посещения) попадают в CRM автоматически.

## П.4. Шаблоны для ботов

**Цель:** спроектировать и реализовать систему шаблонов сообщений для ботов
(Telegram/WhatsApp/VK/СМС/email — состав каналов утвердить).

**Зависит от:** п.3 (CRM — источник данных и триггеров). Отделы «🧩 Шаблоны» админки
(S145/S148: `templates-masks-sms`, `templates-masks-email`, `templates-masks-social`,
`templates-mockups-*`) — уже подготовлены как заглушки: шаблоны логично хранить в psql,
а редактировать в этих разделах админки.

**Шаги:** 1) каталог шаблонов (приветствие, напоминание о занятии, поздравление,
реактивация, ответы на частые вопросы) с переменными `{имя}`, `{день}`, `{время}`;
2) схема хранения + рендер (подстановка, валидация переменных);
3) админка: CRUD + предпросмотр по каналам; 4) тест-рассылка на себя.

**Критерий готовности:** шаблон из админки рендерится с данными клиента и уходит
в тестовый канал без ручных правок.

## П.5. Реализация ботов

**Цель:** реализовать ботов на основе шаблонов (п.4) и данных (п.2/п.3).

**Кандидатные сценарии (уточнить):**
- напоминание о занятии (за N часов, из расписания CRM);
- ответы на частые вопросы (расписание/цены/адрес — из данных сайта);
- запись/отмена занятия через диалог;
- реактивация молчащих клиентов (сегменты по посещениям).

**Шаги:** 1) выбор платформы бота (grammy/telegraf для TG и т.п. — в стеке п.1);
2) диалоговые сценарии; 3) планировщик рассылок (cron PM2-задача); 4) журналирование
отпра­вок в CRM; 5) лимиты/антиспам, отписка.

**Критерий готовности:** боевой бот в одном канале (Telegram) отрабатывает напоминания
и FAQ на реальных клиентах, логи в CRM.
